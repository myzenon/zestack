# Work design (draft)

Decisions made so far. To be tuned later. Based on `work-ledger` and `work-planner` from the human's current harness (no_vibe_agent).

## Decided

- **Work and Task:** in. A Work lives in `.zestack/state/work/<id>/` (see `state-design.md`).
- **Worktree support:** wanted, but later, so the harness can be used sooner. Listed in `README.md` under Later.
- **Tickets** (`client-requirements.md`, links to outside ticket IDs): out.
- **Tool:** exact operations (IDs, state lines, renames) are done by a script, not by the AI editing files. Anthropic's skill guide recommends scripts for this, because they are more reliable than generated code, save tokens, and give consistent results. The AI still writes the prose (Outcome, Approach, notes).
- **Tool language:** Python, standard library only, so there is nothing to install. Works on macOS (`python3` comes with the Xcode command-line tools) and WSL. Bash only for tiny helpers, because a large tool in bash is hard to write and review, and macOS ships bash 3.2.

- **Delivery:** a Work skill named `work-ledger`. The rules go in `SKILL.md`, whose body loads only when the skill is used, and the tool goes in its `scripts/`, which runs without loading its code into context. One folder keeps the rules and the tool versioned together. `CLAUDE.md` names the skill directly, so it's always used instead of depending on description matching. This follows Anthropic's skill guide, and pstack ships its tools the same way. How it's installed is in `playbooks/installation.md` (a link from `.claude/skills/`).
- **Take ideas, not code:** zestack's tool is written new and small, step by step. `work_ledger.py` is a reference for ideas only, because zestack's design may differ.
- **Work ID:** UUIDv7 (random and time-ordered), shown and typed as a short prefix like a git commit. Random, not counted, so a deleted Work leaves no gap to explain and two machines never make the same ID. Python's `uuid` module only has `uuid7()` from 3.14, and macOS has 3.9, so the tool builds the UUIDv7 itself.
- **Top `work.md`:** only what every project in the Work shares. Outcome (the intended finished result), Approach (the agreed direction across projects), Verification (the final check that it's done), and Later (the later list of postponed topics, one line each, so a new session sees them).
- **`<project>/work.md`:** Outcome (this project's part), Work context (relevant paths, each with a short reason), Approach (the direction shared by this project's Tasks), Current task, Tasks (one line per Task), Done when, Verification. Added only when needed: Key decisions, Project state, Blocked on, Pending human action.
- **New Task:** new work goes into the Current task by default. When new work doesn't fit the Current task, the AI must tell the human and suggest a new Task. The AI creates a Task only after the human agrees, never on its own, because a Task split the human didn't choose makes the Work harder to follow.
- **Focus:** the one topic human and AI are on right now, for example "design the Focus system". It can last for many prompts. It works like a meeting under Robert's Rules of Order: one question on the floor at a time, and only the chair (the human) changes it. The problem it solves: the AI moves to a new topic on its own before the current one is settled, so the human loses track.
  - Focus changes only when the human says the current topic is OK, or chooses to switch.
  - When a new topic comes up, the AI warns the human that it shifts the focus, writes it to a later list instead of discussing it, and stays on the current Focus.
  - The later list is required, and the AI tries to clear it. When the current Focus is done, the AI brings up the later list before anything new, like "unfinished business" coming first on a meeting's agenda, and the human picks what's next or drops an item.
  - The behavior is a principle in `CLAUDE.md`. The current Focus is also recorded as a `Focus:` line directly under each Task's title in `<project>/work.md` (per Task, like the current harness, so switching Tasks keeps each one's place), so a new session, a context summary, or another machine continues on the same topic. The AI updates the line when the human says OK to a switch, by editing `work.md` directly. There is no tool command for Focus, because it's one line of prose, not worth code. Whether the AI forgets in practice is to be found out by using it.
- **No states:** the four states from `work-ledger` (`planning`, `implementing`, `blocked`, `completed`) are dropped. In practice the AI forgets to update and read them, and what they say is already visible: `Blocked on` shows blocked, Tasks and Focus show progress. Only completion is recorded, by the tool, when the human closes the Work.
- **Completion:** only the human closes a Work. The tool then renames its folder to `work/completed-<id>/`, so open and completed Works are told apart from folder names alone, without reading every `work.md`. Safe with self-sync, because only `.zestack/` itself is symlinked.
- **Logging:** each Task log line is a pointer plus one short why, for example `4f15f09 — fixed login lock race`. Never a retelling of the commit or diff, because git already holds the story; the log only saves a new session from searching for it.
- **No redirect rule:** dropped, because a redirect is a Focus switch, which the Focus rule already covers.
- **A new decision replaces the old one:** when a new decision changes an earlier one, the same write deletes the old text. No "superseded" or "kept as history" notes, because the AI tends to leave stale text behind, and `work.md` should hold only the current direction. Git holds the history.
- **Task spill:** a Task's notes stay inline in `work.md` while short. Past about 15 lines they move to `task-<id>.md`, and `work.md` keeps a one-line pointer, so `work.md` stays quick to read.
- **Paused:** only the human pauses or resumes a Work. The tool renames the folder: `work/<id>/` is active, `work/paused-<id>/` is paused, `work/completed-<id>/` is done. Folder names alone show every Work's status.
- **Scratch:** each Work has its own `work/<id>/tmp/`, the only place the AI puts scratch files for that Work, so they don't spread across the project. In git mode, `tmp/` is excluded from git (`.zestack/state/work/*/tmp/`, which also covers `paused-` and `completed-` folders), so scratch files never reach the repo. Installation adds the rule. In self-sync mode, `tmp/` syncs like everything else, so scratch files follow the human to any machine.
- **Locking:** every tool command locks the Work while it runs, so two sessions on the same Work (for example, a main session and a subagent) can't overwrite each other's change. The lock is per machine; it doesn't reach across machines through sync.
- **Handoff:** a Work that touches several projects has `work/<id>/handoff.md`, a shared log with one line per round, for passing information between projects. For example: "api: the new endpoint is ready, web can use it." Created only when used. Handoff is for events only, moments in time. An agreement between projects, like an API spec, goes in the top `work.md` → Approach, because it stays true for the whole Work and shouldn't be buried in a log.
- **Protect recorded work:** Work and Task files are durable state. The AI never deletes, truncates, or recreates them to reorganize. If a fix would delete a Task, a Work file, or content that's still current, the AI shows the exact change and waits for the human's OK. Replacing an old decision with a new one is normal upkeep and doesn't need this.
- **Start and resume:** when a session starts without a Work ID, the AI runs the tool's list of open Works, shows the short result, and asks the human to pick one ID or `new`. It reads no Work until the human chooses, so it never guesses which Work is meant. The human can also start directly with `/work-ledger new` or `/work-ledger continue`. The skill keeps the name `work-ledger`, because `work` alone is too vague.
- **PR ownership:** a PR or branch recorded by a Work stays owned by that Work. Review comments, failed checks, and follow-up fixes become a new Task in the same Work (suggested by the AI, created after the human agrees, like any new Task), never a new Work. If the Work was already closed, the AI asks the human before reopening it.
- **Tool commands:** `work new`, `work list [--all]`, `work path`, `work add-project`, `work pause`, `work resume`, `work close`, `work tmp`, `task add`, `task current`, `task list`, `task spill`, `task done`.
- **Task done:** a Task has one marker, `done`, set when the human accepts the Task. No `open` (the default) and no `blocked` (`Blocked on` covers it). Prose (Focus, log lines, handoff, Later, Outcome, Approach) is edited directly, not through the tool.
