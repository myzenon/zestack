# Code conventions

- **No stale code:** When a change replaces old code, delete the old code, old ways, and anything left unused in the same change, because the AI copies whatever it finds, and stale code leads it the wrong way.
- **No comments:** Don't write comments in code, because comments go stale and the AI trusts them anyway. When code needs a comment to be understood, reshape the code instead (rename, extract, add a type) until it's obvious. Keep only: legal or license headers; behavior forced by something outside our control, such as a vendor, platform, or protocol; formatter ignores, and lint suppressions only when the rule is wrong or style-only; doc comments that define a public API; and issue or RFC links for a constraint the code can't express.
- **Smallest change:** Make the smallest change that solves the problem, and put each decision in one place instead of repeating it, because a small diff with one source of truth is what the human can review and understand.
- **No speculative code:** Write code only for cases that really happen, not for cases that might happen someday, such as checks for input the system already prevents. Add a check when a real case shows up, because every extra line is one more line for the human to review.
- **Easy to read:** Keep code quick to understand: inline wrappers and pass-through methods that have only one caller, and prefer returned values over changed state, locals over fields, and fields over globals. A new reader should find where a value comes from and what can change it in under 30 seconds, because the human has to understand every change. When this clashes with the project's `code-design.md`, `code-design.md` wins.
- **Fix root causes:** Fix a bug where it starts, not where it shows up. Reproduce it first, then ask "why" until you reach the wrong decision in the code. A guard, retry, swallowed error, or clamped value at the crash point hides the bug instead of fixing it. When other places have the same fault, report them and ask before fixing them, so the change stays within what the human asked.
- **Test behavior:** A test checks what users of the code can see (return values, errors, readable state, effects on outside systems), not private helpers or internal call order. Keep a test only if it fails when the behavior breaks and still passes when only the internals change, because then a refactor doesn't bring test noise into the human's review.
- **Data shape first:** Before writing logic, show the human the data shape it works on (types, fields, structures), for example `Order { id, items: Item[], status: "draft" }`, so they can agree or correct it in seconds instead of decoding it from the code later.
- **Two sketches across modules:** For a change that crosses module boundaries, trace every part it touches, then show the human two different sketches (types, signatures, module boundaries) before writing code, and let them pick. Prefer the sketch where each piece of state has one owner, each task has one way to do it, and callers need to know the least. This keeps the human choosing the structure instead of finding it in the diff.
- **Match the surrounding code:** New code follows the patterns and style of the file and code around it, so the human's review is about what changed, not about style differences.
